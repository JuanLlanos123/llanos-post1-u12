ADR-001: Mantener capas simples para persistencia y reutilizar Observer para notificaciones
- Estado: Aceptada
- Fecha: 2026-11-15
- Contexto: Sistema de solicitudes de reembolso de gastos
Contexto
El sistema separa el procesamiento de solicitudes, las validaciones, los cálculos por categoría y las notificaciones de cambios de estado. Para decidir si conviene migrar a una arquitectura Hexagonal, se evalúa por separado la persistencia y la notificación, aplicando el criterio de la Guía de Contenido (sección 6.2): la arquitectura Hexagonal se justifica especialmente en sistemas que sobrevivirán tres años o más con cambios de infraestructura.

En la persistencia, SolicitudReembolsoService depende actualmente de RepositorioSolicitudesJpa. No existe un plan de cambiar el motor de base de datos.

En las notificaciones, el servicio ya se encuentra desacoplado de los notificadores concretos mediante la interfaz ObservadorCambioEstado. Actualmente hay tres interesados: el empleado, Contabilidad y Auditoría Interna. Además, Contabilidad anunció que integrará un sistema externo el próximo trimestre.
Decisión
1. Persistencia: mantener capas simples
Se decide mantener la dependencia de SolicitudReembolsoService hacia RepositorioSolicitudesJpa, sin introducir por ahora una interfaz adicional RepositorioSolicitudes ni un adaptador JPA.

La razón es que no existe un plan actual de cambiar el motor de base de datos ni evidencia de que la persistencia vaya a experimentar cambios de infraestructura durante un horizonte de tres años o más. Introducir un puerto y un adaptador en este momento añadiría abstracciones y código de delegación sin responder a una necesidad concreta del proyecto.

Si aparece un plan real de migración de motor, persistencia alternativa o coexistencia de varios mecanismos de almacenamiento, se revisará esta decisión y se evaluará extraer el puerto RepositorioSolicitudes.
2. Notificaciones: conservar Observer y encapsular la integración externa
Se decide conservar ObservadorCambioEstado como contrato entre el procesamiento de solicitudes y los interesados. No se introducirá ahora una segunda interfaz de puerto ni se migrará todo el paquete procesamiento.notificacion a una arquitectura Hexagonal.

Para la integración de Contabilidad, se incorporará o adaptará un observador concreto —por ejemplo, NotificadorContabilidadExterno— que implemente ObservadorCambioEstado y encapsule la comunicación con el sistema externo. La condición de negocio existente se mantiene: este observador solo ejecuta la acción de programación de pago cuando el nuevo estado es APROBADA; los demás cambios de estado no generan esa acción. El empleado y Auditoría Interna continúan recibiendo los eventos según sus responsabilidades.

El servicio que publica los cambios de estado no debe conocer el cliente HTTP, SDK, protocolo ni detalles del proveedor externo. Si la integración llega a requerir sustituir proveedores, varios destinos externos o cambios frecuentes de infraestructura, se revisará la conveniencia de introducir un puerto específico para el cliente de Contabilidad y un adaptador de infraestructura.
Consecuencias
Consecuencias positivas
- Se evita introducir un puerto y un adaptador JPA sin una necesidad de cambio de persistencia identificada.
- Se conserva una arquitectura sencilla y proporcional a las necesidades actuales del proyecto.
- SolicitudReembolsoService mantiene su dependencia actual de RepositorioSolicitudesJpa, haciendo explícita la decisión de no abstraer todavía la persistencia.
- La interfaz ObservadorCambioEstado permite agregar o sustituir observadores sin modificar el servicio que publica los cambios de estado.
- La integración externa de Contabilidad queda encapsulada en un observador concreto y no obliga a que el servicio de solicitudes conozca detalles del sistema externo.
- La regla de que Contabilidad solo actúe ante el estado APROBADA permanece localizada en su observador.
Consecuencias negativas
- SolicitudReembolsoService continúa acoplado a JPA y a la implementación concreta del repositorio; una futura migración de base de datos podría requerir cambios en el servicio.
- Las pruebas de SolicitudReembolsoService deben trabajar con la abstracción disponible en el repositorio JPA o con mocks de esa dependencia; no se obtiene todavía independencia completa de la tecnología de persistencia.
- La integración externa de Contabilidad añade complejidad dentro de su observador concreto, por ejemplo, manejo de errores de comunicación, tiempos de espera, autenticación y reintentos.
- Si la integración externa cambia repetidamente o se incorporan varios proveedores, la solución basada solo en el observador podría resultar insuficiente y requerir un puerto y un adaptador específicos.
Alternativas consideradas
A. Arquitectura Hexagonal completa para todas las dependencias
Introducir puertos para persistencia y notificación, con adaptadores concretos para JPA y para el sistema externo.

Motivo de no selección: no hay un plan de cambiar el motor de base de datos y ya existe una abstracción útil para los observadores. La migración completa agregaría complejidad que no está justificada por los datos actuales del proyecto.
B. Capas simples para persistencia y Observer existente para notificaciones
Mantener el repositorio JPA directo en el servicio y utilizar ObservadorCambioEstado para integrar el sistema externo mediante un observador concreto.

Motivo de selección: responde a la situación real de cada dependencia: persistencia estable sin cambio de motor previsto y notificaciones con un contrato de extensión ya existente y una integración externa próxima.
Criterios para revisar esta decisión
Se revisará este ADR si ocurre cualquiera de las siguientes situaciones:
- Se aprueba un plan de migración del motor de base de datos o se requiere soportar más de una tecnología de persistencia.
- La integración de Contabilidad exige varios proveedores, protocolos o destinos externos, o se vuelve probable que la infraestructura de notificación cambie repetidamente durante tres años o más.
- Los detalles técnicos del sistema externo empiezan a filtrarse hacia SolicitudReembolsoService o hacia el contrato ObservadorCambioEs
